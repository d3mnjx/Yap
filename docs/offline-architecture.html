Offline rewrite / Architecture field guide

A live conversation.
Even between connections.

Yap keeps chat, drafts and outgoing work on the device. The server accepts changes durably and brings the browser back into sync when the connection returns.

Browser + ASP.NETNative JavaScript modules
SQLite-backed acceptance
Local work survives interruption

Drafts, replies, uploads and mutations use account-bound browser storage.

Retries keep the same identity

Operation receipts let the server recognize work it has already accepted.

Recovery stays straightforward

Incremental updates merge changed records; gaps reload a bounded window. Older history is versioned separately.

Current communication: one bootstrap validates the account and supplies the active window. Catalog, missing inactive windows and bounded media warming run independently. Live changes carry only affected records. Shell v34 uses IndexedDB schema 4, preserving drafts and queues. See the communication guide for startup, transport and priority diagrams.

01 /

One application. Two places for state.

The browser owns the chat experience and pending work. The existing ASP.NET application remains the authority for identity, permissions and accepted messages.

Runtime architecture

Connected

Local writes happen first. HTTP sends operations; SignalR delivers personalized deltas and live updates. Both acceptance paths converge through the same snapshot queue.

On a small screen, scroll the diagram sideways. The connection switch illustrates behavior; it does not change any running server.

What works without a connection

Read cached conversations and media, switch cached rooms, preserve drafts, and queue text, replies, attachments, edits, deletes and reactions for later acceptance.

What still needs the server

Initial login, uncached history and media, new server lookups, presence/typing, external providers and Settings/Admin. Queued actions are authorized again when sent.

STEP 01 / 05
If the acknowledgement gets lost

The browser retries the same operation ID and payload. The server recognizes its receipt and returns acceptance without repeating the mutation. A deleted message stays deleted; replaying an old receipt cannot recreate it.

03 /

Four clocks, four responsibilities.

Asynchronous work can finish after an account change, reconnect or navigation. These independent guards decide whether its result still belongs.

PERSISTED / ACCOUNT

Whose work is this?

The local account lease fences storage writes. An old task cannot write into another account after a purge or account replacement.

identity.epoch → storage transaction
SERVER / SNAPSHOT

Is this newer authority?

A process epoch and per-record sequence checks order authority across tabs and restarts. A delayed old response cannot restore stale data.

serverEpoch + sequence → per-record ordering
PAGE / CONNECTION

Is this still our connection?

Each connection attempt has a generation. Stopping a connection invalidates its callbacks before they can affect the replacement.

connectionGeneration → network callbacks
PAGE / RENDER

Is this still the current view?

Rendering has a separate generation. Delayed draft reads cannot overwrite a newer room selection or a more recent render.

renderGeneration → DOM and draft restoration

Two more boundaries to preserve. Older history carries a content version, including in inactive rooms. Read acknowledgements carry the highest arrival checkpoint actually observed, so an offline read cannot clear newer unseen messages.

05 /

Keep state with its owner.

Focused modules make asynchronous behavior easier to change. The coordinator stays explicit where account, connection and render ordering must agree.

app.js

Owns account, connection, snapshot queue, routing and render coordination. These lifecycles stay together because their ordering matters.

composer.js

Owns draft writes, reply selection, restoration, submission and attachment input. User actions capture their original account and conversation.

messages.js

Owns timeline rows and hydrated image URLs. Active editors and playing media survive unrelated updates.

Keep the contracts visible. contracts.js documents account, snapshot and outbox shapes for editors. Runtime authorization stays on the server; storage transactions enforce account ownership and ordering.

06 /

Validation and operating limits.

The architecture is designed for occasional outages. Its correctness comes from a few durable boundaries and the regression checks around them.

Maintained regression checks

  • Server authorization, persistence, receipt replay and migrations.
  • Browser sends, reply races, history reconciliation and cached media.
  • Draft/outbox survival, worker activation and offline reload.
  • Retained Settings/Admin integration and instrumented PWA behavior. Coverage is scoped in the feature reference.

Boundaries still worth knowing

  • Device installation, external push/providers, Safari and broader storage/accessibility coverage remain separate checks.
  • Browser storage can be evicted; it is not a backup. Cold offline access has no elapsed-time limit for an unlocked saved account.
  • Recipient unread/notification side effects follow message acceptance. A later failure can miss an unread increment.
  • Keep deployed browser namespaces stable. Add runtime assets to the worker and bump its shell version; keep APIs and tokens out of static caches.
