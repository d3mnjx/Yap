Offline rewrite / Communication explained

One app.
Two browser runtimes.

Chat loads its data over HTTP, then opens a dedicated SignalR connection for updates. Retained Razor pages run through a separate Blazor Server circuit. This guide follows the actual startup order and shows what travels where.

HTTPChat SignalRBlazor ServerBrowser local
HTTP

Ask, change, acknowledge

Load the shell and current state. Send messages and actions. Fetch history. Upload media. Receive an explicit response.

Chat SignalR

Stay up to date

Receive personalized message deltas and live presence. Report visibility, status and typing on /hubs/chat.

Blazor Server

Run retained Razor pages

Welcome, Login, Settings and Admin keep server-side components. Their events and render updates use /_blazor.

01

The connection map

The browser runs a different document when you move between chat and Settings/Admin. Both use the same ASP.NET application, accounts and shared services.

SignalR is an application protocol/library; WebSockets is a transport.

Starting a SignalR connection itself uses HTTP negotiation, normally followed by a WebSocket upgrade. The custom chat client leaves transport selection to SignalR, so Server-Sent Events or long polling may be used when supported. Blazor also uses SignalR internally, with its own framework protocol and transport negotiation. “HTTP API versus SignalR” describes the application paths, not mutually exclusive network technologies.

02

From the first visit to live chat

Choose an entry point. The numbers show execution order; asset loading, worker installation and background HTTP work can overlap.

Visiting the site root

Authenticated / without a return URL serves chat directly. Guests and explicit return-URL flows retain Welcome/Login and their Blazor circuit.

  1. 01
    HTTP

    GET / → authenticated chat shell

    Program.cs checks the authenticated user and returnUrl. For the ordinary signed-in visit it returns the static client document, avoiding the Welcome circuit and subsequent document navigation. Root remains network-first in the worker for authentication and rollback.

    Browser → ASP.NET → chat document
  2. 02
    Browser local

    Prepare local storage

    Service-worker registration runs independently. Read account-bound IndexedDB schema 4; conversation bodies are stored separately from the global header. Local drafts/outbox remain independent of server data.

    Browser ↔ IndexedDB
  3. 03
    HTTP

    One GET /api/chat/bootstrap

    Cookie validation, memory-only CSRF token, live ticket, global settings, conversation summaries and the selected recent window share one response. Matching cached account/epoch/revision omits unchanged active message bodies. No separate startup /session or /sync is needed.

    Browser → HTTP API → browser
  4. 04
    Browser local

    Apply authority and enable sending

    Restore same-account history/drafts, merge bootstrap and render. Start the outbox immediately. Normal writes reuse credentials: one POST returns the receipt and affected message/conversation authority.

    IndexedDB → DOM; outbox → HTTP
  5. 05
    HTTP

    Start optional background work

    Catalog, saved-read batches, missing recent windows and PWA setup do not gate sending or hub startup. Window recovery prioritizes the active conversation, then unread ones; foreground work and navigation cancel or pause obsolete downloads.

    Background HTTP alongside active chat
  6. 06
    Chat SignalR

    Connect to /hubs/chat

    SignalR negotiates over HTTP and opens an available transport, normally WebSockets. Transport fallback is retained. This connection carries chat updates, not Blazor render batches.

    Browser ⇄ chat hub
  7. 07
    Chat SignalR

    WatchActivity + WatchChanges

    WatchActivity registers presence and selected conversation in its streaming invocation. WatchChanges supplies cached revisions and receives authorized deltas; its first packet is a quiet baseline, including when nothing changed. Neither subscription awaits a separate Join/Report response.

    Two streams on one connection
  8. 08
    Browser local

    Merge and render affected data

    Persist changed conversations and acknowledge operations atomically. Inactive arrivals update the sidebar without rebuilding the active timeline. Load media lazily; bounded background warming yields to foreground work.

    Delta → IndexedDB → selected DOM
Yes: the API comes before the chat hub.

The main path is /bootstrap → apply active state → sender.start() + background work → hub.start() → WatchActivity + WatchChanges. Catalog, saved reads, missing windows and PWA setup do not block sending. Transport negotiation still takes network exchanges; changing from HTTP to a hub invocation would not eliminate the propagation time for a write acknowledgement.

03

Which feature uses which path?

Chat API paths share the /api/chat prefix. A connection to the hub does not mean that messages are sent through it.

16 features shown

Path Feature Request / method and meaning
HTTP Open chat GET /, /lobby, /chat, /room/{id}, /dm/{username}

Authenticated root without returnUrl and direct chat routes serve index.html. Prepared canonical chat routes use the shell cache immediately.

HTTP Authenticate and bootstrap GET /api/chat/bootstrap?path=…

One response: account/session, summaries and active window. Cached matching revisions omit unchanged message bodies. Credentials stay in memory.

HTTP Refresh expired credentials GET /api/chat/session

Shared refresh after explicit CSRF rejection, plus a 30-second background account-cookie check. No preflight per ordinary write.

HTTP Recover missing recent windows GET /api/chat/windows/{id}

Cancellable queue: selected first, then unread. New arrivals stream independently of this queue.

HTTP Send text, replies and media references POST …/conversations/{id}/messages

Stable operation ID and content. Compact receipt + affected authority; no full-account snapshot or follow-up GET.

HTTP Edit, delete, react; batch queued work POST …/messages/{messageId}/actions · POST /api/chat/operations

Desired reaction membership and stable operation IDs. Up to 16 already queued non-media operations / 48 KiB share a request without delaying the first send.

HTTP Acknowledge observed messages POST /api/chat/reads

Coalesce for 300 ms; batch up to 100 checkpoints. Unloaded summaries cannot mark unseen messages read.

HTTP Open DM / load older history POST /api/chat/dm/{username} · GET …/history · GET …/messages/{id}

Cached navigation is local. Older pages and reply targets fetch on demand with authorization; ordinary arrivals preserve loaded unlimited history.

HTTP Catalog, emoji and GIFs GET /api/chat/catalog, /gifs, /gifs/library, /gifs/categories · POST /emoji/recent, /gifs/favorite, /gifs/select

Catalog does not block startup. Emoji recents coalesce for 500 ms; provider search needs connectivity.

HTTP Upload and display media POST /api/tus · HEAD/PATCH upload URL · GET/Range media

Final PATCH can carry completion references; account-owned receipt GET remains a loss/reload fallback. Thumbnail/poster warming is bounded; no speculative full-video download.

Chat SignalR Receive messages, edits, metadata and unread changes /hubs/chat → WatchChanges

Changed records and removals, deduplicated authors, revisions and sequence. Authorized per account; no account-wide message history per arrival.

Chat SignalR Presence, viewing state and typing /hubs/chat → WatchActivity; ← Report, Typing, SetStatus

Register + initial view in one stream invocation. Presence sends changed people/fields; typing avoids repeating the presence list. Report/Typing do not wait for replies; explicit status awaits confirmation.

Blazor Server Welcome, Login, Settings and Admin Page GET → App.razor → /_blazor

Retained interactive server components. The ordinary authenticated root bypasses Welcome; guest/returnUrl flows still use it.

HTTP Authentication and PWA handoff /auth/* · /invite/{code} · /pwa-launch · /manifest.webmanifest

Cookies, redirects and no-store personalized responses remain online. No anonymous shell cache for tokens.

HTTP Push registration / installation /api/push/* · POST /api/chat/pwa/installed

Setup runs independently of chat. Later Web Push uses the browser push service and worker, not either SignalR connection.

Browser local Drafts, queues and rendering IndexedDB · Cache Storage · DOM · Web Locks

One account coordinator across tabs, up to three independent conversations, at most one upload. The worker does not send the outbox. Chat has no Blazor render batches.

04

A message takes two return paths

The write is HTTP. Its effect reaches connected readers through SignalR deltas. Both paths meet in the same client reconciliation code.

What the stream contains

WatchChanges emits ChatUpdate: changed conversation metadata/messages, removed IDs, deduplicated authors, optional global settings, base/current revision, server epoch and sequence. A newly created inactive DM includes its latest message immediately.

Shared events wake an authorized snapshot comparison, coalesced for 15 ms. A ten-second timeout catches other changes and rechecks authentication; unchanged state sends no data. Snapshots still exist internally. Gaps or restart recover bounded windows, without a persistent event log. Older loaded history survives ordinary arrivals; mutations invalidate its bounded cache.

Why HTTP acceptance matters

A response identifies acceptance or a specific failure. If it disappears after the database commit, the browser retries the same operation ID. The persisted receipt prevents accepting the same operation twice.

sender.start() runs before hub startup, so HTTP sends can succeed while the live channel is unavailable. Updates from other users need the stream or a later HTTP catch-up.

Traffic priority and remaining costs

Three conversations can send independently, with one upload maximum and ordering inside each conversation. Foreground writes/history pause background windows and media. Media warming covers the last three visited conversations, last 30 messages, at most 8 MiB per document/account, 4 MiB per file and a 32 MiB account cache; Save-Data disables it.

One ordinary POST still has network propagation latency. HTTP keep-alive does not imply a fresh TCP/TLS connection per send. The removed session preflight eliminates one serial round trip. The simulated 900 ms comparison measures startup, delivery and cache costs against the frozen original; real-deployment telemetry remains unmeasured. Server-side snapshot comparison remains a potential scaling cost. Older-history mutations conservatively trigger bounded refresh rather than a second persistent event-log protocol.

05

Where App.razor still fits

App.razor and Routes.razor are unchanged from the pre-rewrite baseline 0cb6742. The rewrite routes chat documents around that host through explicit HTTP endpoints.

Retained Razor pages

App.razor hosts interactive server components

The document itself supplies HTML, styles and scripts. HeadOutlet and Routes each declare InteractiveServerRenderMode(prerender: false).

That means those components execute interactively on the server after the circuit starts. Their initial component output is not prerendered into the document. It does not mean the whole response is empty HTML.

Routes.razor uses Router and RouteView. Button events such as Settings changes invoke C# handlers over the circuit; render batches update the browser. This is server interactivity, not WebAssembly.

Standalone chat

index.html is the chat host

MapOfflineChat() maps ordinary chat URLs to the static client document. It loads the SignalR JavaScript library and app.js, with no blazor.web.js and no Razor render-mode declaration.

JavaScript owns the DOM. Shared styles, including the extracted component stylesheet, preserve the existing appearance; using those styles does not instantiate Razor components.

The old RoomChat.razor and DmChat.razor source remains, but their @page directives are removed. They do not serve the current chat routes.

Moving between the two worlds

Inside chat, known conversation navigation uses history.pushState and local rendering. The Settings/Admin links load another document and start Blazor. Returning to chat uses a full navigation, including explicit forceLoad: true in retained pages. The old document’s connection closes; chat creates its own HTTP bootstrap and hub lifecycle again.

07

Disconnection is different for each path

The browser owns unsent work. A socket disconnect, HTTP failure and a lost Blazor circuit are different events.

HTTP

A write can be retried

The sender keeps the operation in IndexedDB until accepted or marked failed for review. A lost response can be retried with the same ID. It reuses the current memory-only token and sends the expected account. The server checks both; explicit CSRF rejection refreshes once, without replay under a changed account.

Chat SignalR

Reconnect means catch up

There is no withAutomaticReconnect() here. app.js schedules its own roughly three-second reconnect and runs HTTP synchronization again before opening a fresh hub connection.

WatchActivity is transient. It does not restore old typing events from the queue. Bootstrap catch-up establishes a quiet notification baseline.

Blazor Server

A circuit must reconnect

Retained pages depend on the server circuit and use the Blazor reconnect UI/policy. Their interactivity is not supplied by the chat snapshot cache or outbox.

Chat’s service worker does not turn Settings/Admin into offline pages.

What you should expect in browser DevTools
  • Chat: the static document and assets, one /api/chat/bootstrap, parallel optional /catalog and missing windows, then /hubs/chat/negotiate and usually a WebSocket request under /hubs/chat.
  • Send: an HTTP POST …/messages, plus delta frames arriving on the chat connection. Uploads add tus requests before message acceptance.
  • Typing: SignalR invocation frames; no HTTP POST …/messages. With an HTTP fallback transport, those same hub messages appear in transport requests instead of a WebSocket Frames panel.
  • Settings/Admin: blazor.web.js and framework /_blazor traffic. Ordinary Razor button events are circuit messages, not individual chat API requests.
  • Visit / then enter chat: an ordinary authenticated visit serves the chat document directly. Guests and explicit returnUrl flows retain the welcome circuit. Enable Preserve log to compare the document lifecycles.
  • Offline: cached shell assets and stored state, failed network attempts, no successful live stream. A later reconnect begins with one HTTP bootstrap again.
Current deployment behavior: forwarded public scheme/IP are accepted without a proxy allowlist by default; an allowlist is optional. Forwarded Host is ignored. Optional PublicOrigin overrides per-user login-link origins. Chat writes retain account-bound antiforgery. Browser-marked cross-site API writes and hub requests are rejected, but missing metadata and public/internal URL differences are tolerated. See the deployment guide.
